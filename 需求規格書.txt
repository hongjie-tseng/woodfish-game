請協助我使用 VS Code 開發一套可以在手機瀏覽器遊玩的「敲木魚」遊戲，並部署到兩台現有 Ubuntu Server VM。

這是國立中央大學資訊管理研究所的網路管理課程作業，目的不只是完成遊戲，而是透過真實玩家產生網路流量，利用 Zabbix 與 ntopng 展示網路監控功能。

**請特別注意：基礎設施已經架設完成，禁止在沒有必要的情況下重新設計、重新安裝或破壞現有設定。**

# 一、專案背景與目的

## 1.1 課程作業

需要建置並實際展示開源網路管理工具，例如：

- Zabbix
- ntopng

需要能夠觀察與比較伺服器的網路流量、封包、協定、CPU、記憶體及其他可監控指標。

預計約 60 名同學使用自己的手機，透過 4G／5G 或 Wi-Fi 進入網頁遊戲。

同學會分成 A、B 兩隊，連接不同的遊戲伺服器。

整個專案有兩種遊戲：

1. 敲木魚（由我負責開發）
2. 流量拔河（由另一位同學獨立開發）

本次開發範圍**只有敲木魚**，但必須與流量拔河共存，不能占用或修改流量拔河預留的服務 Port。

## 1.2 核心實驗概念

讓 A、B 兩組玩家產生真實的 HTTP 流量，再比較兩台伺服器的：

- Network throughput（網路吞吐量）
- Received / Sent traffic（接收及傳送流量）
- Packet rate（封包速率，若監控項目可取得）
- CPU utilization
- Memory utilization
- Network connections（若監控工具可取得）
- Protocol distribution（依 ntopng 實際可見的流量判讀）

必須區分「遊戲應用程式統計」與「網路監控工具觀測值」，不得將 HTTP 請求數直接宣稱為封包數。

# 四、遊戲功能需求

## 4.1 遊戲定位

這是一個手機網頁敲木魚遊戲。

操作必須簡單，進入網址後不用註冊、不用登入、不用設定，就能直接開始敲擊。

畫面使用繁體中文。

視覺風格：

- 現代、簡潔、精緻
- 木魚主題
- 適合手機單手操作
- 按鈕與主要木魚圖案要夠大
- 避免過多文字與操作
- 可以有輕量動畫與音效
- 版面應有遊戲感，而不是一般管理後台

## 4.2 首頁畫面

至少包含：

1. 遊戲標題「電子敲木魚」
2. 中央大型可點擊木魚
3. 個人累積敲擊次數
4. 全隊累積敲擊次數
5. A 隊或 B 隊標示
6. 伺服器連線狀態
7. 簡短操作提示

A、B 隊畫面使用相同程式碼，但可以透過設定檔區分顯示的隊伍名稱及主題色。

不需要讓玩家自己選隊，因為掃描不同 QR Code 就會進入不同伺服器。

## 4.3 敲擊互動

每次玩家點擊木魚：

1. 立即觸發短暫的敲擊動畫。
2. 可播放短音效，但必須支援靜音。
3. 向後端發出一次真實 HTTP POST 請求。
4. 後端確認請求成功後更新已確認的計數。
5. 顯示玩家的個人敲擊數及全隊總數。

**核心要求：每一次有效敲擊都應產生一次獨立 HTTP 請求。**

不得為了節省流量而將多次敲擊合併為單一請求。

不得只在前端增加數字而不向伺服器發送請求。

但也不能故意產生無意義的超大封包或大量背景請求來製造流量。

為了避免手機快速連點時漏算，請設計合理的非同步請求及排隊機制，不要讓畫面卡頓。

需考量請求失敗、重試和重複計數問題，建議使用唯一敲擊 ID，讓後端支援冪等處理。

## 4.4 計數系統

需要：

- 個人敲擊次數
- 該伺服器的全隊總敲擊次數
- 本回合的敲擊次數
- 目前回合狀態

A、B 兩台伺服器的統計必須相互獨立。

不需要建立中央計數伺服器，也不需要讓 A、B 互相同步分數。

個人識別可使用瀏覽器產生的匿名 UUID，保存在 localStorage。

不需要姓名、學號、Email 或其他個人資料。

## 4.5 比賽回合

考慮課堂展示的操作流程，需要提供基本回合控制。

至少支援：

- 開始新回合
- 暫停或結束回合
- 重設本回合計數
- 保留或清除累積計數

請設計僅限管理者操作的控制方式，優先提供伺服器本機 CLI 管理指令，避免公開無驗證的重設 API。

不要為此導入大型後台、OAuth 或複雜帳號系統。

開始與結束回合的方式需要容易在課堂現場操作。

## 4.6 音效與動畫

可以用 CSS 動畫與簡單的原創音效完成。

不要依賴外部 CDN 或不確定授權的圖片、音效。

若需要圖片素材，優先使用自行製作的 SVG 或可合法使用的本地資源。

音效必須符合手機瀏覽器的播放限制。

音效播放失敗不能影響敲擊或 HTTP 請求。

## 4.7 網路斷線處理

如果手機暫時無法連線：

- 不應造成前端崩潰。
- 顯示清楚的連線狀態。
- 區分已確認及尚未確認的敲擊。
- 不要假裝伺服器已收到請求。
- 不要在重新連線後無限制地重送大量請求。

需有合理的 Timeout、錯誤處理及重試策略。

## 5.2 API

至少規劃：

GET /

取得遊戲首頁。

GET /health

回傳伺服器健康狀態，例如：

- status
- team
- server_time

POST /api/tap

接收單次敲擊事件。

GET /api/stats

取得目前的遊戲統計。

GET /api/config

取得前端需要的公開設定，例如隊伍名稱、回合狀態。

請自行定義合理的 JSON Schema，使用 Pydantic 驗證輸入。

API 必須有適當的 HTTP 狀態碼與例外處理。

同一瀏覽器的重試請求不得導致同一敲擊重複計數。

## 5.3 資料儲存

使用 SQLite。

建議考慮：

- WAL 模式
- 交易一致性
- 多個請求同時寫入
- 避免不必要的資料庫鎖定
- 避免每次統計查詢掃描大量歷史資料

不需要保留每一次敲擊的完整個人行為歷史。

只需儲存必要的統計資料及短期去重資訊，避免資料庫無限制增長。

請在 README 說明資料庫如何初始化、備份及重設。

## 5.4 效能需求

預估玩家約 60 人，分成 A、B 兩隊。

假設每人平均每秒敲擊 4 次。

總計約：

240 次敲擊／秒。

平均分配到兩台伺服器：

每台約 120 次敲擊／秒。

以上是設計與壓力測試目標，不代表已經驗證實際效能。

請考量統計輪詢額外產生的流量，以及手機網路延遲。

前端統計更新可以每 1～2 秒輪詢，不需要每次敲擊都重新抓取全隊統計。

不需要引入 WebSocket，除非可以清楚證明有必要。

應提供可以在本機執行的基本負載測試工具，驗證請求成功率、延遲及計數正確性。

不要對正式公開網址直接執行高負載測試，除非取得我的明確同意。

# 八、網路監控相關要求

本專案的重要目的，是讓 Zabbix 和 ntopng 能觀察真實遊戲流量。

## 8.1 Zabbix

Zabbix Agent 已安裝完成。

Host：

game-a

game-b

已經可以取得 CPU、記憶體及網路監控項目。

請不要重新安裝 Zabbix。

如果後續需要監控更多指標，先分析現有項目是否足夠。

可在 README 說明建議觀察：

- ens33 inbound traffic
- ens33 outbound traffic
- CPU utilization
- Memory utilization
- Packet rate（若現有或新增項目支援）

因為遊戲回合可能只有幾十秒，需提醒監控輪詢間隔可能影響圖表細節。

## 8.2 ntopng

ntopng 安裝在 VM 1。

目前監控 VM 1 的 ens33。

真實手機連線路徑：

手機 → Cloudflare → VM 1 的 cloudflared → VM 2／VM 3

需注意：

- 不能假設 ntopng 一定能看見玩家原始 IP。
- 不能假設 VM 1 可以看到手機到 Cloudflare 的所有原始封包。
- Cloudflare Tunnel 會影響 ntopng 可見的通訊端點與協定。
- 不可把遊戲 HTTP request 數直接當成實際網路封包數。
- 不可假設 VM 1 的 ens33 能單獨觀察所有 A、B 伺服器互相無關的網路流量。

如果監控功能受到 NAT、Tunnel 或 VMware 虛擬交換網路限制，請明確指出，而不是產生虛假的統計。

## 8.3 可觀測性

程式應提供適當的應用程式日誌，至少能觀察：

- 每秒敲擊請求數
- 成功與失敗請求
- 回合狀態
- 伺服器啟動與錯誤

避免每次敲擊都輸出過多冗長日誌，造成不必要的磁碟負載。

若需要額外提供監控 API，應避免不必要的資料暴露及額外架構複雜度。
